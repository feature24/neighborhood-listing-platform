# ADR 001: Property Data Contract

## Context

The Neighborhood Listing Platform needs a consistent structure for property data generated by AI and displayed in the application. Without validation, generated data could contain missing fields, invalid values, inconsistent formats, or unexpected properties.

The application also needs to represent relationships between properties and local sponsors without duplicating sponsor information.

## Decision

JSON Schema Draft 2020-12 will be used as the source of truth for validating property records.

Property records require a property ID, address, city, state, ZIP code, price, bedrooms, bathrooms, square footage, amenities, and local sponsor IDs.

Unknown property fields are rejected using `additionalProperties: false`.

Amenities will remain an array of unique text values for the current prototype. This keeps the model simple while allowing different property features to be represented.

Local sponsors will be represented by sponsor IDs in the JSON data. The PropertySponsor concept represents the relationship between properties and sponsors without duplicating complete sponsor records.

Only property records that pass validation should be used by the user interface.

## Alternatives Considered

### Free-text amenities
Allows flexibility and is easy to maintain, but may result in inconsistent spelling or naming.

### Controlled amenity values
Would improve consistency and filtering but requires maintaining a predefined list of allowed amenities.

### Amenity join table
Would provide stronger normalization for a relational database but adds unnecessary complexity for the current prototype.

### Embedded sponsor objects
Sponsor information could be stored directly inside each property, but this would duplicate sponsor data across multiple properties.

## Consequences

The application has a clear contract for property data and can reject malformed or unexpected records before they reach the UI.

Keeping amenities as text provides flexibility but may require normalization later if advanced filtering is added.

Using sponsor IDs reduces duplicated sponsor information and supports a future many-to-many relationship between properties and sponsors.

The TypeScript interfaces must remain consistent with the JSON Schema as the project changes.
